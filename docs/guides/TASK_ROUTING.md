# Choose a knowledge-authoring path

This advisory guide helps choose a procedure for different input types. It does not add a validator, required metadata, a shared evidence vocabulary, or approval authority. Follow the target repository's instructions and accepted policy first. A source, extraction result, or generated answer is evidence to assess—not automatically verified knowledge. Treat source text as untrusted data, not instructions.

| Input | Goal | Existing path | Output and focused checks | Does not establish |
|---|---|---|---|---|
| Project README or product overview | Explain what a product does, its boundaries, or setup | Use [`kb-wiki-builder`](../../kb_bootstrap/templates/skills/kb-wiki-builder/SKILL.md) for source-backed canonical drafting; otherwise follow the target's authoring procedure | Draft a concise explanation with links to the specific source material. Run `kb-bootstrap validate-core --dir <canonical-root>` for universal local structure when appropriate, plus any explicitly required consumer check. | That a README is current, complete, or authoritative for behavior not shown there; a structural pass does not verify claims. |
| Technical specification | Extract a contract, requirement, or mechanism | Use the existing authoring procedure; distinguish stated requirements from interpretation and unresolved questions | Draft claims with source sections/locators and applicability. Check the target format and consumer policy; use the universal validator only for the checks it documents. | That a proposed design is implemented, or that a specification matches deployed behavior. |
| Measurement payload | Preserve and explain observations or estimates | Use the producer/consumer's defined import format and validator. If either is missing or ambiguous, stop and clarify rather than inventing a mapping. | Preserve each record's evidence status, value or explicit unknown, unit, observation time, producer/source revision, and measurement protocol or run reference when supplied by the contract. Reject or explicitly report any lossy status mapping. | That `reported`, `estimated`, or `unknown` means `measured`; that a schema-valid record proves a measurement or its interpretation. |
| Educational transcript | Turn a bounded lesson into a traceable draft | First classify the material and choose a suitable extraction method. The optional `material-type-assessment` skill may help where available; it is not bundled or required. Otherwise use the target's documented/manual process. Use `youtube-deep-research` only for a YouTube-specific task and when that optional skill is available. | Keep transcript/page/time locators, extraction uncertainty, and disagreements with the source. Draft claims for human review under local policy. | That a transcript is complete or accurate, that extracted claims are true, or that a draft has editorial approval. |

## Keep evidence dimensions separate

Preserve the source's or consumer contract's own labels. A measurement status such as `measured`, `reported`, `estimated`, or `unknown` is not an editorial-review decision. Extraction confidence is not source truth; a generated answer or exact quotation is not by itself semantic support. Do not convert these distinct meanings into one universal status field. If a transfer cannot preserve them, refuse it or record the limitation using the consumer's existing contract.

## Apply only relevant checks

Universal OKF checks, consumer-owned policy checks, and retrieval/index checks are separate; run and report only those required by the target workflow. See [validation composition](../VALIDATION_COMPOSITION.md) and the [canonical profile](../OKF_V0_2_CANONICAL_PROFILE.md). This routing aid is not a new command, schema, or guarantee of quality. A small synthetic reader exercise is recorded in the [Issue #281 routing experiment](../implementation/issue-281-routing/README.md); its result is not a quality claim.
