# Consumer and upstream contribution workflow

Use this workflow when a repository generated by `kb-bootstrap` has its own
consumer repository and optionally references `ozand/kb-bootstrap` as an upstream
framework.

## Decide who owns the change

Route the work to the **consumer repository** when it changes project-specific
knowledge, configuration, documentation, or application behavior.

Route the work to **kb-bootstrap upstream** when it changes the reusable CLI,
generator, packaged templates, generated skills, or framework documentation.

If ownership is ambiguous, stop before creating a branch, commit, Issue, or pull
request. Verify the intended repository with its maintainer.

## Consumer-owned work

Work from the consumer checkout and target its repository explicitly. Configure
the checkout so an ordinary `git push` defaults to the consumer `origin`:

```bash
kb-bootstrap doctor --repo example/consumer-project
git config --local remote.pushDefault origin
git switch -c docs/example-consumer-change
git config --local branch.docs/example-consumer-change.pushRemote origin
```

Verify the effective configuration before pushing:

```bash
git config --local --get remote.pushDefault
git config --local --get branch.docs/example-consumer-change.pushRemote
git remote get-url --push origin
git push --dry-run
```

Both Git config values must report `origin`. Inspect only the sanitized repository
identity in a receipt; do not publish a token-bearing push URL. Then push and open
the consumer pull request explicitly:

```bash
git push -u origin docs/example-consumer-change
gh pr create \
  --repo example/consumer-project \
  --base main \
  --head docs/example-consumer-change
```

A branch-level `pushRemote` takes precedence over `remote.pushDefault`. Use the
branch setting to keep downstream branches on `origin`; do not set it to upstream
for ordinary consumer work.

Before reporting completion, verify that the pull request head commit and base
repository match the consumer Issue.

## Upstream-owned work from a consumer repository

Do not implement reusable framework changes on the consumer branch. Use a
separate upstream checkout or Git worktree so consumer state and upstream history
cannot be mixed.

### Option A: separate checkout

```bash
git clone https://github.com/ozand/kb-bootstrap.git ../kb-bootstrap-upstream
cd ../kb-bootstrap-upstream
kb-bootstrap doctor --repo ozand/kb-bootstrap
git switch -c feat/example-upstream-change
```

### Option B: verified upstream worktree

Use this only when the local repository already contains a verified
`ozand/kb-bootstrap` remote reference. Do not guess which remote is upstream.

```bash
git remote get-url upstream
git fetch upstream main
git worktree add ../kb-bootstrap-upstream-worktree upstream/main
cd ../kb-bootstrap-upstream-worktree
kb-bootstrap doctor --repo ozand/kb-bootstrap
git switch -c feat/example-upstream-change
```

Keep live `.pi/`, `.agents/`, credentials, and other runtime state in the original
checkout. Never use a broad untracked-file stash as a generic branch-switch
backup.

## Create and verify the upstream pull request

Push the branch to an explicitly verified repository you are authorized to use.
Do not change the consumer checkout's `remote.pushDefault` to make an upstream
push convenient. From the separate upstream checkout/worktree, verify the push
remote and name it explicitly:

```bash
kb-bootstrap doctor --repo ozand/kb-bootstrap
git remote get-url --push origin
git push --dry-run origin feat/example-upstream-change
git push -u origin feat/example-upstream-change
gh pr create \
  --repo ozand/kb-bootstrap \
  --base main \
  --head feat/example-upstream-change
```

If the upstream contribution checkout pushes to a fork, explicitly name that fork
remote and use an owner-qualified PR head. Never rely on an inherited consumer
push default.

If the branch is hosted in a fork, use an explicit owner-qualified head such as
`contributor:feat/example-upstream-change`.

Verify the resulting pull request before claiming delivery:

```bash
gh pr view <number> \
  --repo ozand/kb-bootstrap \
  --json url,state,baseRepository,baseRefName,headRepository,headRefName,headRefOid
```

The base repository must be `ozand/kb-bootstrap`, the base branch must be `main`,
and the reported head commit must match the pushed upstream contribution commit.
A commit that exists only in the consumer repository is not upstream completion
evidence.

Run the read-only completion check before closing or reporting an Issue:

```bash
# Commit already merged into the default branch
kb-bootstrap check-completion \
  --repo ozand/kb-bootstrap \
  --commit <commit-id>

# Commit still reachable only from an associated pull request
kb-bootstrap check-completion \
  --repo ozand/kb-bootstrap \
  --commit <commit-id> \
  --pr <number>
```

The command exits non-zero for a wrong repository, unavailable commit, unrelated
commit, or mismatched pull request. It does not close Issues, create pull requests,
change remotes, rewrite history, or modify branches.

## Sanitized completion evidence

A safe receipt may include:

- public repository name;
- branch name;
- commit ID;
- public Issue or pull-request URL;
- test/build result summary.

Do not include credentials, token-bearing remote URLs, private payloads, local
runtime checkpoints, or unsanitized logs.

If repository identity, branch target, authentication, or commit containment is
missing or mismatched, stop and report the mismatch. Do not create or retarget a
pull request by guessing.
