## Context

Accepted ADR-031/036 bind a knowledge document to explicitly validated retained evidence. ADR-036's optional fragment is a representation-ID-bound inclusive UTF-8 line range. The current `resolve_evidence_binding` validates that locator against the baseline representation, then compares mapped current representations by digest. It does not extract/compare fragment bytes or report candidate locations. A changed representation digest therefore does not answer whether exact fragment bytes remain at the old location, uniquely moved, repeated, or absent. ADR-036's reference shape is closed and ADR-042 validates it strictly; changing either wire contract in this increment is out of scope.

Research was recorded before this draft in #128 comment [6561814106](https://github.com/ozand/kb-bootstrap/issues/128#issuecomment-6561814106). It was based on Issue #128, accepted ADR-031/036/040/042, and the resolver at `7499f3761a8b746ef29ac9c5ef72b421fb53f61b`. No consumer or user data was read. Current access already has trusted permission callbacks, caller-selected paths, full envelope validation, safe bounded selected-file reads, expected-revision checks, and no discovery/network/write. The proposal must preserve these seams and the immutable binding input.

## Decision

If accepted, add one additive public entry point, `resolve_evidence_binding_with_fragment_continuity`, with the same keyword-only arguments and trusted callbacks as `resolve_evidence_binding`. It runs one authorized resolver operation and returns `{"resolver_report": <unchanged ADR-036 report>, "fragment_continuity": <companion result>}`. It accepts no resolver report, path, snapshot, or permission token from the caller beyond the existing resolver inputs. ADR-036 report fields/bytes and ADR-042 accepted input/output shapes remain unchanged; callers pass `resolver_report` unchanged to `compose_evidence_review_worklist` and retain the companion result alongside that worklist.

The wrapper is exactly `{"resolver_report":<ADR-036 report>,"fragment_continuity":<companion>}`. The companion has exactly one of these shapes: `{"status":"NOT_APPLICABLE","observations":[]}` when the valid resolver report has no fragment-bearing references; `{"status":"COMPLETE","observations":[...]}` when all fragment-bearing references were handled, including non-blocking unassessable outcomes; or `{"status":"BLOCKED","reason":<closed code>}` with no observations on any failure. If a report mixes located and unlocated references, `COMPLETE` contains observations for only the located references; unlocated rows simply have no fragment-continuity observation. Each observation has exactly these keys: `binding_id`, `source_id`, `representation_id`, `observed_sha256`, `fragment` (the unchanged `{representation_id,start_line,end_line}` locator), `current` (null if no mapping; otherwise the explicit `source_id` and `representation_id`, plus `observed_sha256` only when that mapped retained representation resolves), `outcome`, `baseline_offset`, and `current_offsets` (at most 100 ascending integer byte offsets; empty when unassessable or no match). Its identity is the corresponding ADR-036 report row identity `(binding_id, source_id, representation_id, observed_sha256)` plus the exact fragment locator. ADR-036 rejects duplicate baseline source/representation pairs within a binding; the same evidence may occur in different bindings, whose unique `binding_id` keeps their observations distinct. Do not join by source/representation alone or collapse repeated references. It includes no payload, copied fragment text, absolute path, or newly selected path. A resolver `BLOCKED` report is embedded unchanged with companion `{"status":"BLOCKED","reason":"resolver_blocked"}`. The companion blocked reason vocabulary is exactly `resolver_blocked`, `invalid_fragment`, `unsafe_or_inaccessible_path`, `baseline_identity_mismatch`, `resource_limit_exceeded`, `match_limit_exceeded`, `snapshot_unavailable`, `serialization_limit_exceeded`. Permission denial continues to raise the resolver's existing `PermissionError` before reads, not a new report or authority path.

Observations appear in the same order as their corresponding fragment-bearing reference rows in the unchanged ADR-036 `resolver_report.references` array, omitting rows without a fragment and preserving every remaining row. Do not independently sort or re-key observations. ADR-036 specifies reference order by baseline source ID, representation ID, observed digest, binding ID, then evidence-array position; because a binding ID is unique and a binding cannot repeat a baseline pair, this report order disambiguates all valid rows and is deterministic for a valid binding input. The companion inherits that stable report order; it adds no separate ordering contract.

Continuity is assessable only when an explicit current mapping resolves to a retained representation in the fully validated current envelope. No explicit mapping yields `unassessable_no_mapping`; an explicit mapping whose target is absent from the validated current envelope yields `unassessable_current_missing` (even where the existing resolver classifies the reference `missing`). Neither implies deletion. Empty extracted fragments yield `unassessable_empty_fragment` and no offsets; they are not treated as matching everywhere. Invalid UTF-8, invalid/out-of-range locator, baseline digest mismatch, malformed inputs, stale expected revisions, inaccessible paths, or exceeded bounds block the entire companion result with no partial observations.

For assessable input, extract the selected baseline line range from the exact validated UTF-8 representation bytes. The fragment is the byte slice from the first selected line's start through the last selected line's content end, excluding that final line's LF or CRLF delimiter; internal delimiters remain bytes. Its baseline byte offset is the start of the first selected line, zero-based from the representation beginning. No decoding normalization, Unicode normalization, whitespace folding, or newline conversion is performed. Search only the explicitly mapped, validated current representation bytes for exact occurrences of those fragment bytes. Enumerate overlapping matches with a linear-time prefix-function/KMP scan and report offsets in ascending byte position, zero-based from the current representation beginning; bind them to the observed current digest/path already established by the resolver.

For an eligible non-empty fragment with an explicit mapped current representation, outcome is exactly one of: `exact_at_baseline_offset` (one match at the baseline byte offset), `unique_moved_match` (one match at a different offset), `ambiguous_exact_matches` (two or more matches, including overlaps), or `no_exact_match` (zero matches). `unassessable_no_mapping`, `unassessable_current_missing`, and `unassessable_empty_fragment` are the only non-blocking unassessable outcomes. These names make no claim that the cited text remains semantically applicable. A match at the old offset is only byte continuity; it does not establish surrounding conditions, meaning, or correctness. No automatic relocation, binding rewrite, deletion inference, or semantic matching occurs.

The entry point performs the existing permission checks exactly once, before any filesystem access, and uses the existing resolver's selected-input path list, validated envelope identities, path containment/reparse checks, expected-revision checks and report result. Implement the entry point as one internal resolver operation with a private, non-caller-constructible per-invocation byte-snapshot context: the existing selected-file validation/read seam records the exact bytes and observed digest after its existing safety checks, and both report derivation and fragment matching consume those same bytes. No snapshot object crosses the public API, survives the call, or grants authority. The resolver must not be called a second time. Do not reconstruct current evidence by rereading `raw_path` values out of the completed report: those report paths are output identifiers, not new caller instructions. Do not accept a new path, snapshot, callback, root, token, or authorization flag for the companion. Reuse exact caller-selected retained paths and the same trusted callbacks only; no extra path or read scope is authorized. If validated bytes cannot be shared through this seam, return deterministic companion `BLOCKED` (`snapshot_unavailable`) with no observations; never bypass guards or weaken resolver operation.

Proposed limits: 64 KiB extracted fragment bytes; at most 64 MiB per source representation as already bounded by the selected-file cap; current report/reference limits and the existing 256 MiB aggregate selected-byte ceiling remain authoritative; at most 100 emitted current offsets per fragment. Count each snapshot once per actual representation input even when both report and continuity consume it. If this invocation's snapshot/aggregate budget is exceeded, preserve the resolver's existing ADR-036 `BLOCKED` report and return companion `BLOCKED` (`resource_limit_exceeded`), with no partial observations. Never allow companion work to turn a resolver `BLOCKED` into `COMPLETE`, or the converse. Search only the already-selected mapped current representation; no traversal, other representation, source discovery, origin access, network, cache or write is permitted.

Use a linear-time prefix-function/KMP scan, reporting at most 100 offsets; if a 101st match exists, return `BLOCKED` (`match_limit_exceeded`) without truncated observations. Bound the number of fragment-bearing references by the existing maximum total report references (999), and reject more before search. Proposed closed companion failure reasons are `resolver_blocked`, `invalid_fragment`, `unsafe_or_inaccessible_path`, `baseline_identity_mismatch`, `resource_limit_exceeded`, `match_limit_exceeded`, `snapshot_unavailable`, and `serialization_limit_exceeded`; failures contain no OS/parser detail or partial observations. Trusted permission denial is the existing exception and occurs before reads. The 64 KiB fragment ceiling and companion serialization ceiling of 8 MiB are additional proposed limits; ADR-031/036's established selected-file, aggregate and report ceilings continue to apply. These are proposed limits, not current runtime guarantees.

The companion output is transient and separate from both accepted report formats. Observation rows contain the exact baseline reference identity/digest and fragment locator and, only for a resolved explicit mapping, current IDs/digest; they contain outcome and bounded offsets only, no representation payload, absolute path, or copied fragment text. They cannot be fed back as authority or mutate bindings/knowledge. ADR-040 lineage and ADR-042 worklist behavior remain separate; the caller passes the unchanged resolver report to the existing composer and keeps its returned worklist unchanged beside the companion result. The companion never changes resolver states or lineage classifications.

## Consequences

A reviewer can distinguish exact byte continuity at the original offset, one exact moved occurrence, duplicate/overlapping occurrences, and no exact match, while retaining the accepted resolver's explicit mapping and access boundaries. Identical fragment bytes can occur in unrelated contexts; this result intentionally cannot resolve that ambiguity semantically. Changed surrounding context remains a human review concern.

## Non-goals

No changes to ADR-031/036/040/042, existing resolver outcomes or worklist schema; no text similarity, semantic equivalence, inference, automated relocation, binding/knowledge mutation, claim database, extra path discovery, lineage inference, lifecycle transition, or conclusion that absence of an exact fragment means deletion or retraction.

## Rollback

Before acceptance, withdraw this proposal. No runtime, consumer data, accepted ADR, or binding record is changed. If accepted and implemented, a superseding decision must preserve existing binding/report compatibility; no automatic migration or deletion is authorized.
