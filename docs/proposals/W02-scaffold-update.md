# Proposed: bounded safe scaffold repeat

**Status:** Proposed — not accepted, not implemented
**Related:** GitHub issues #123 and #121; W02 characterization report; ADR-002;
ADR-004

## Context

The W02 synthetic reproductions show that ordinary initialization silently
overwrites a user-edited `qmd.json` and installed `kb-lookup` skill while
reporting success. Generated bytes become consumer-owned once installed; their
location alone is not permission to replace them.

Safe repeat is an urgent, bounded problem. Template upgrade, historical
baseline metadata, and adoption of existing consumers are different lifecycle
problems. This proposal therefore separates a first safe-repeat increment from
those later designs.

## Proposed first increment: safe repeat

### Fixed managed destination set

For the selected `single` or `umbrella` layout, the initializer must build a
bounded map from the trusted installed package inventory plus the generated QMD
outputs. It must never discover managed destinations by walking the consumer
directory. At the currently observed package revision, the complete map is:

- `qmd.json`;
- `qmd/collections/wiki.yaml`;
- `qmd/collections/raw.yaml`;
- `.agents/skills/kb-wiki-builder/SKILL.md`;
- `.agents/skills/qmd-operator/SKILL.md`;
- `.agents/skills/kb-lookup/SKILL.md`;
- `.agents/skills/market-research/SKILL.md`;
- `.agents/skills/market-research/assets/brief-template.md`;
- `.agents/skills/market-research/assets/report-template.md`;
- `.agents/skills/market-research/evals/evals.json`;
- `.agents/skills/market-research/references/feature-matrix.md`;
- `.agents/skills/market-research/references/formats.md`;
- `.agents/skills/market-research/references/jtbd-cjm.md`;
- `.agents/skills/market-research/references/parallel-studies.md`;
- `.agents/skills/market-research/references/positioning.md`;
- `.agents/skills/market-research/references/sources.md`;
- `.agents/skills/market-research/references/technology.md`;
- `.agents/skills/market-research/references/ux-patterns.md`;
- `.agents/skills/market-research/scripts/capture_page.py`;
- `.agents/skills/market-research/scripts/check_research.py`;
- `.agents/skills/market-research/scripts/extract_markdown.js`;
- `.agents/skills/market-research/scripts/find_links.py`;
- `.agents/skills/market-research/scripts/grep_claim.py`; and
- `.agents/skills/market-research/scripts/new_research.py`.

The package inventory, not a manually maintained sample of top-level skill
files, is authoritative when constructing the map. Packaging tests must fail if
an included regular file (after the existing `__pycache__`/`*.pyc` exclusions)
lacks a mapped destination. If future package or QMD generation adds another
ordinary unconditional write, the generated closed map and its tests must cover
it before release.

Paths that are neither generated QMD outputs nor counterparts of packaged
inventory entries are unrelated to this comparison. In particular, user KB
articles, root or nested `AGENTS.md`, custom skills, and consumer-added files
inside a packaged skill directory are ignored and preserved. They are not
`extra` conflicts and are never removed merely because of directory membership.

### Delegated destinations

The project-lessons contract is not governed by template-byte equality here.
ADR-002 assigns `kb/lessons/SCHEMA.md`, `kb/lessons/index.yaml`,
`lesson-stores.json`, and `.agents/skills/kb-capture/SKILL.md` to the separate
`enable-project-lessons` command: complete valid state is a byte-preserving
no-op, partial or invalid state blocks, and all-absent state uses bounded
exclusive enablement. The proposed safe-repeat implementation must delegate
classification and any enablement of those four paths to that accepted command's
helper (or preserve an equivalent call boundary) rather than compare them with
template bytes.

This is proposed delegation, not a description of current ordinary
`--with-project-lessons` behavior. Today that initializer branch copies
`kb-capture/SKILL.md` unconditionally, only conditionally copies the other three
artifacts when absent, and does not first perform ADR-002's four-artifact
validation. The proposal neither weakens ADR-002 nor treats the existing flag as
if it already implemented that contract.

Managed `AGENTS.md` content remains governed by ADR-004's marker-bounded update
contract. Human-authored content outside its managed block is not scaffold
state. Existing `.gitignore` content remains governed by the current additive,
marker-based rule and is never required to equal a template. Empty marker files
and directories retain their existing additive/idempotent handling. The first
increment must invoke or preserve these accepted semantics rather than replace
them with whole-file byte comparisons.

### Read-only plan and classification

Before mutation, compute one complete plan under the explicit target root.
Reject absolute or escaping destinations, symlinked path components, and
non-regular managed destinations. Classify every path in the fixed set as:

- `matching`: a contained regular file whose bytes equal the bytes the selected
  package would generate now;
- `content differs`;
- `missing`; or
- `destination type unsafe`.

Do not scan for extra consumer paths. Do not infer that differing bytes are an
old template merely because current package bytes exist. Diagnostics list only
sorted relative managed paths and stable categories; they expose neither file
contents nor absolute paths.

### First initialization, no-op, and conflict

When all fixed destinations are absent and every delegated contract is eligible
for its own first-install behavior, first initialization may proceed using its
reviewed creation behavior. Pre-existing unrelated paths do not affect
eligibility.

When every fixed destination is `matching` and each delegated contract reports
its own valid no-op, ordinary repeat succeeds without staging or writing any
file. Unrelated paths remain byte-for-byte untouched.

If any fixed destination is `content differs`, `missing`, or
`destination type unsafe`, block the entire ordinary repeat before mutation and
preserve the full tree. A mixture of matching and missing paths is partial
scaffold state, not permission to fill gaps. A delegated contract's blocking
result also blocks the overall repeat without allowing the fixed set to mutate.
There is no broad `--force`, automatic merge, normalization, or repair behavior.

## Bounded implementation plan

The first implementation needs no metadata file, installed-version registry,
updater, or adoption workflow:

1. Build the closed destination map and expected bytes from the trusted packaged
   inventory and generated QMD outputs entirely in memory, without walking the
   consumer tree.
2. Ask accepted lesson, routing, managed-`AGENTS.md`, and `.gitignore` contracts
   for their existing classification; do not reinterpret their files.
3. Perform contained, non-symlink, regular-file checks and byte comparisons for
   the fixed map without writing or creating directories.
4. Return a successful no-op only for a complete matching/delegated-valid state.
5. Otherwise return one sanitized blocking receipt before calling any existing
   overwrite/copy path.
6. Keep the current first-initialization creation path behind a complete
   absent-state classification; hardening its publication and rollback may be
   reviewed independently and must not weaken the repeat guard.

This increment prevents the demonstrated destructive re-entry without claiming
multi-path transactionality or solving template migration.

## Acceptance for the first increment

Safe repeat can be reviewed and accepted independently when tests demonstrate:

1. the fixed destination set is exact and complete for every supported layout;
2. an identical complete repeat is a byte-preserving no-op with no staging;
3. a valid JSON edit to each QMD destination and an edit to every packaged skill
   file class—including `SKILL.md`, script, reference, asset, and eval—block the
   complete repeat and preserve the tree;
4. a missing, partial, non-regular, escaping, or symlinked fixed destination
   blocks before mutation with relative-only diagnostics;
5. unrelated KB articles, `AGENTS.md`, custom skills, and a consumer-added file
   beside packaged scripts/references/assets neither block nor change;
6. complete valid lesson data/routing survives according to ADR-002, including
   populated indexes and local routing choices, while partial/invalid state has
   that contract's existing blocking result;
7. managed `AGENTS.md`, unmanaged surrounding content, existing `.gitignore`
   content, directories, and markers retain their accepted contracts;
8. a conflict in either the fixed set or a delegated contract causes zero
   writes across the entire planned repeat; and
9. receipts contain no absolute paths, contents, credentials, or temporary
   implementation details.

Tree manifests and injected write/staging spies should prove the no-write
claims. These tests do not depend on any updater interface or historical
baseline registry.

## Future proposal: update and adoption

Explicit template update remains Proposed separately. A future design may use a
read-only preview followed by a separately explicit update, replacing a file
only when its current bytes match a trustworthy baseline for a recorded
installed template version. It must define immutable baseline availability,
metadata format, CLI spelling, per-file eligibility, path rechecks, staging,
publication, recovery, and sanitized receipts before acceptance.

Existing consumers have no trustworthy installed-template metadata. They must
not be silently adopted by treating current bytes as historical proof. A future
adoption/migration procedure must establish provenance without discarding
consumer edits. Unknown baselines and modified managed files must remain
blocking. No updater or adoption behavior is needed to accept or ship the first
safe-repeat guard.

Likewise, automatic merging and managed subranges for whole-file templates are
outside this increment. A separately reviewed bounded region could follow
ADR-004, but current whole-file destinations have no such contract.

## Failure and rollback boundary for future updates

No portable operation makes multiple paths atomically visible together or
excludes hostile writers. Any future updater must complete preflight and
staging before publication, immediately recheck source identity and bytes,
publish with bounded same-directory primitives, and clean up only
invocation-owned artifacts. Restoration may use only verified invocation-owned
backups and must never overwrite a subsequent foreign change. It must disclose
any final state it cannot prove and must not claim global atomicity.

These requirements are future acceptance gates for update, not dependencies of
immediate safe-repeat acceptance.

## Alternatives rejected

- **Keep unconditional overwrite:** destroys consumer-owned edits, as reproduced.
- **Treat every extra path as a conflict:** incorrectly claims unrelated
  consumer content as scaffold state.
- **Require all generated-looking files to equal templates:** violates accepted
  lesson, routing, `AGENTS.md`, and `.gitignore` contracts.
- **Skip every existing managed path:** can bless a partial or incompatible
  scaffold and misleadingly report success.
- **Broad force flag:** expands destructive authority without provenance.
- **Wait for updater metadata:** leaves the demonstrated re-entry hazard in
  place and creates a circular dependency on an unaccepted interface.
- **Promise transactionality:** per-file primitives do not provide an atomic
  multi-path transaction on arbitrary filesystems.

## Consequence if later accepted

Ordinary re-entry becomes conservative: exact current generated bytes are a
no-op, conflicts inside a small closed set block, unrelated consumer files are
ignored, and accepted specialized contracts remain authoritative. Template
upgrade and adoption remain separate future work. Until owner review accepts an
implementation contract, this document changes no public behavior or status.
