# Proposed: safe scaffold repeat and explicit template update

**Status:** Proposed — not accepted, not implemented
**Related:** GitHub issues #123 and #121; W02 characterization report; ADR-002;
ADR-004

## Context

The W02 synthetic reproduction shows that ordinary initialization silently
overwrites a user-edited `qmd.json` and installed `kb-lookup` skill while
reporting success. A generated file becomes consumer-owned once installed; its
location alone is not proof that its current bytes are disposable.

The initializer also has no durable record of which template revision produced
an existing file. It therefore cannot reliably distinguish an unchanged old
template from a consumer file that happens to differ from the current template.
Safe repeat and intentional template upgrade are separate operations.

## Proposed decision

### 1. First initialization

Before mutation, compute a complete plan for the selected layout and options.
Every destination must be relative to one explicit target root. Reject absolute
or escaping destinations, symlinked path components, and existing non-regular
destinations. Classify every planned destination as absent or existing before
creating any file.

First initialization is eligible only when every exclusive scaffold destination
is absent. Pre-existing unrelated paths outside the plan remain untouched.
Pre-existing planned paths block with a sorted list of relative paths rather
than being adopted or overwritten. An explicit, narrowly specified adoption
contract could be proposed later; it is not part of this decision.

Stage all planned bytes before publication. Publish absent files exclusively so
a race-created destination is never overwritten. On failure, remove temporary
files and only published files whose identity and bytes still prove they belong
to this invocation. Report any owned artifacts that could not be removed. This
is bounded compensating rollback, not an all-filesystem transaction.

### 2. Ordinary safe repeat

An ordinary repeat performs a read-only plan and comparison first:

- if every expected generated file exists as a contained regular file and its
  bytes equal the selected package template/generated bytes, return a successful
  no-op;
- additive directories or empty marker files already matching the contract are
  also no-ops;
- if an expected destination is missing, extra, type-changed, symlinked, or has
  different bytes, block before all mutation and report its relative path and a
  stable category; and
- never infer that differing bytes are stale merely because a current template
  exists.

Ordinary repeat must not update templates, fill a partial scaffold, normalize
content, remove unknown files, or expose file contents or absolute paths in its
receipt.

### 3. Conflicting user edit

Any byte difference at a managed whole-file destination is a conflict. Preserve
the file byte-for-byte and block the entire planned operation. Report sorted
relative paths and categories such as `content differs`, `missing`, or
`destination type unsafe`. Do not offer a broad `--force` or overwrite switch.

Whole-file templates have no managed subrange, so automatic merging is outside
this proposal. A future template may define an independently reviewed bounded
managed region, following ADR-004, but that would be a distinct contract.

### 4. Explicit template update

Template upgrade is an explicit operation, separate from initialization, and is
preceded by a read-only preview. The preview identifies the requested source and
target template versions and lists each proposed `create`, `replace`, `no-op`, or
`conflict` by relative path without writing.

Replacement is eligible only when the current destination bytes match a known
baseline for the consumer's recorded installed template version. The updater
must have packaged, immutable baseline bytes or digests for that version; it
must not guess from Git history, timestamps, or the current template. A missing
or unrecognized baseline blocks. Any user-modified managed file blocks the whole
update unless a later, file-specific merge contract is accepted.

After a conflict-free preview, a separately explicit update invocation repeats
the full preflight, stages all replacement bytes in their destination
directories, and rechecks path safety, file identity, and exact source bytes
immediately before each bounded publication. Existing files are replaced using
same-directory atomic replacement where supported; absent destinations use
exclusive publication. A source change detected after preview or during update
blocks rather than retries or merges automatically.

Update metadata itself is a versioned, contained scaffold artifact. It records
only the installed template identity and the digests needed for later comparison;
it is not authority to overwrite a mismatching destination. Its exact format and
CLI spelling remain an implementation-design gate, not an accepted interface in
this proposal.

## Failure and rollback boundary

No portable operation makes multiple paths atomically visible together or
excludes hostile writers. The implementation must minimize and disclose this
limit:

1. finish a complete non-mutating preflight;
2. stage complete bytes and flush them before publication;
3. publish only after immediate source-state rechecks;
4. on failure, remove owned newly created files and temporary files;
5. for already replaced files, attempt restoration only from invocation-owned,
   verified backups without overwriting a subsequent foreign change; and
6. report, by relative path, every published or restored result and any path
   whose final state cannot be proven.

An implementation may instead block multi-file replacement until a stronger
bounded recovery design is reviewed. It must not claim global atomicity,
unconditional rollback, or safety against a writer acting after the last
controllable check.

## Proposed acceptance cases

This proposal would be ready for acceptance only with tests demonstrating:

1. first init creates the expected bytes for each supported layout and option;
2. identical repeat is a byte-preserving no-op with no staging;
3. one edited QMD file, one edited skill, and each other managed class block the
   complete repeat and preserve the full tree;
4. missing, partial, non-regular, escaping, and symlinked destinations block
   before mutation with relative-only diagnostics;
5. preview is read-only and deterministically lists the complete intended delta;
6. explicit update succeeds only from a recognized exact baseline;
7. user edits, unknown baselines, changes after preview, and changes at injected
   recheck seams block without overwrite;
8. injected stage, flush, publish, and cleanup failures preserve pre-existing
   data and accurately disclose owned partial work;
9. unrelated consumer files, project lessons, managed `AGENTS.md` content, and
   existing `.gitignore` content remain byte-for-byte unchanged; and
10. receipts contain no absolute paths, contents, credentials, or temporary
    implementation details.

Tree manifests and SHA-256 comparisons should cover unchanged, modified,
partial, interrupted, and successfully updated fixtures. Platform-specific
atomic/exclusive primitives require explicit capability tests and fail-closed
behavior when unavailable.

## Compatibility and migration limits

Existing consumers lack trustworthy installed-template metadata. They must not
be silently enrolled by treating current bytes as historical proof. Initially,
they may use safe repeat only when every current byte equals the selected
generated result. Explicit upgrade remains blocked until an independently
reviewed adoption/migration procedure establishes a baseline without discarding
consumer edits.

`enable-project-lessons` and `agents-governance` retain their accepted, narrower
contracts. This proposal does not change their behavior, migrate consumer data,
delete runtime state, install software or models, perform Git/GitHub operations,
or accept a public CLI/metadata format.

## Alternatives rejected for this proposal

- **Keep unconditional overwrite:** destroys consumer-owned edits, as reproduced.
- **Skip every existing path:** can bless a partial or incompatible scaffold and
  misleadingly report success.
- **Overwrite only files differing from the package:** treats evidence of an
  edit as permission to destroy it.
- **Broad force flag:** expands destructive authority without establishing
  provenance or a per-file conflict decision.
- **Automatic three-way merge:** no historical baseline exists for current
  consumers, and semantic merging of JSON, YAML, Markdown, and scripts requires
  separate reviewed contracts.
- **Promise transactionality:** staging and atomic per-file replacement do not
  provide an atomic multi-path transaction on arbitrary filesystems.

## Consequence if later accepted

Ordinary re-entry becomes conservative and predictable, while upgrades require
an explicit, reviewable intent and recognized baseline. The cost is that partial
or historically untracked scaffolds block and require a future bounded adoption
workflow. Until owner review accepts a contract and implementation, this document
changes no public behavior or policy.
